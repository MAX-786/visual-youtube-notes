# PDF export with vector diagrams

Research for wayfinder ticket #8 (part of #1). Question: how should the backend produce a PDF of a Note whose Diagram is embedded as vector graphics, given the spec's constraints (section 12: "Render diagrams as vector graphics in PDF"; Markdown export is a ZIP with local SVG assets; section 13: Go API, separate Go worker, Docker Compose on a 4 vCPU / 24 GB host; tablet-first layout; Hindi/Devanagari and mixed-script text).

Date of research: 2026-09-04. Every claim below is cited to a primary source (official docs, repos, package registries). Where a fact could not be verified against a primary source it is marked **unverified**.

## 1. Framing

The Diagram is canonical JSON, never a bitmap (spec 7.2). For export the pipeline must therefore be:

```
Diagram JSON  ──layout──►  SVG (one per Note revision)  ──►  PDF page(s) with the SVG as vectors
                                     └──►  Markdown ZIP asset (same SVG file, unchanged)
```

Whatever produces the SVG (the same layout engine the PWA uses, run server-side or precomputed from the persisted `layout{}` positions) is shared by both export paths. The open question is only the last arrow: how to get that SVG plus the surrounding note text into a PDF, as vectors, with correctly shaped Devanagari.

Three families were compared:

- **A. Pure-Go PDF library** that also parses SVG (or at least draws paths) — fpdf, gopdf, unipdf, oksvg/rasterx, tdewolff/canvas.
- **B. Server-side SVG-to-PDF converter** (native binary or WASM) whose output page is then placed into a Go-built PDF — resvg, svg2pdf (Rust), rsvg-convert, svg2pdf.js/jsPDF (Node), Typst.
- **C. Headless Chromium** printing an HTML rendering of the Note (inline SVG) to PDF — gotenberg, chromedp, go-rod, Puppeteer/Playwright.

## 2. Hard requirements that decide the outcome

### 2.1 Devanagari needs an OpenType shaping engine

Devanagari cannot be rendered by mapping code points to glyphs one at a time. Microsoft's OpenType Devanagari specification describes a shaping engine that performs cluster analysis, glyph reordering (pre-base matras, reph) and applies a sequence of GSUB/GPOS features (nukt, akhn, rphf, blwf, half, vatu, cjct, pres, abvs, blws, psts, haln, abvm, blwm): <https://learn.microsoft.com/en-us/typography/script-development/devanagari>. Any PDF producer that lacks a HarfBuzz-class shaper will produce visibly wrong Hindi (unreordered matras, missing conjuncts). This single criterion eliminates most of family A.

### 2.2 Fonts and their license

- `fonts-noto-core` on Debian trixie ships `NotoSansDevanagari-Regular.ttf`, `NotoSansDevanagari-Bold.ttf`, `NotoSerifDevanagari-Regular.ttf`, `NotoSerifDevanagari-Bold.ttf` under `/usr/share/fonts/truetype/noto/`; package download 11.9 MB, installed 42.6 MB: <https://packages.debian.org/trixie/all/fonts-noto-core/filelist>, <https://packages.debian.org/trixie/fonts-noto-core>.
- `fonts-deva` is a 3 kB meta-package pulling seven Devanagari font packages (fonts-deva-extra, gargi, lohit-deva, nakula, sahadeva, samyak-deva, sil-annapurna): <https://packages.debian.org/trixie/fonts-deva>. Not needed if Noto is used.
- Noto Sans Devanagari is under the SIL Open Font License 1.1, copyright The Noto Project Authors: <https://raw.githubusercontent.com/notofonts/devanagari/main/OFL.txt>. The OFL FAQ (1.12) states embedding in documents, in full or subset, is permitted and does not change the document's license (1.13): <https://openfontlicense.org/ofl-faq/>. Embedding Noto subsets in exported PDFs is therefore fine.

### 2.3 Vector vs raster

"Vector" here means the PDF contains path and text operators for the diagram, not an image XObject. Text ideally stays text (selectable/searchable, matching spec 7.2 "All diagram text is selectable and searchable"), which requires the producer to embed a subset font and emit a ToUnicode mapping; converting glyphs to outlines keeps the drawing vector but loses selectability.

Takeaway: the credible converter path is **rsvg-convert to a one-page PDF, then gofpdi/fpdf composes the note**. ## 5. Family C: headless Chromium printing the note page

### 5.1 What Chromium's PDF printer does

- The DevTools `Page.printToPDF` command exposes `paperWidth`/`paperHeight` (inches), four margins, `landscape`, `scale`, `printBackground`, `pageRanges`, `headerTemplate`/`footerTemplate`, `preferCSSPageSize`, `generateTaggedPDF`, `generateDocumentOutline`, and `transferMode` (base64 or stream): <https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-printToPDF>.
- Chromium's print pipeline records pages through `MetafileSkia`, whose class comment reads "This class uses Skia graphics library to generate a PDF or MSKP document": <https://chromium.googlesource.com/chromium/src/+/main/printing/metafile_skia.h>. Skia's PDF backend emits native vector paths and text; only specific effects (image filters, non-gradient shaders, some blend modes) are rasterized, and image filters cause "text-as-text is lost": <https://skia.org/docs/user/sample/pdf/>. Practical consequence: an inline `<svg>` with paths and `<text>` prints as vectors with real text, as long as the diagram avoids SVG filters.
- Text shaping and font embedding are Chromium's (HarfBuzz + fontconfig); the container only needs the fonts installed (section 2.2).

### 5.2 Page layout control

- CSS `@page` `size`, `margin`, `page-orientation`, `:first/:left/:right`, and named pages are Baseline 2024: <https://developer.mozilla.org/en-US/docs/Web/CSS/@page>. `break-inside: avoid` is Baseline since 2019: <https://developer.mozilla.org/en-US/docs/Web/CSS/break-inside>.
- Page-margin boxes (`@top-center` etc.) with `counter(page)`/`counter(pages)` shipped in Chrome 131: <https://developer.chrome.com/blog/print-margins>. This gives "Page 3 of 7" running footers in pure CSS; alternatively `headerTemplate`/`footerTemplate` from printToPDF.
- Tablet-oriented layout is just CSS: e.g. `@page { size: 210mm 297mm }` or a landscape 4:3 page for tablet reading, with `preferCSSPageSize: true`.

### 5.4 Memory and isolation

- Gotenberg's minimum guidance is 512 MiB; Playwright warns Chromium can OOM in Docker without `--ipc=host` (or an enlarged `/dev/shm`). On the 24 GB host with two concurrent Jobs this is not a constraint, but Chromium must live in its own service (or the worker image), never in the API image, and should have a memory limit and `--init` for zombie reaping (Playwright docs; gotenberg noted zombie processes before 8.15.2).
- Only the worker (already the "heavy" image with `yt-dlp`/FFmpeg per spec 13) or a dedicated `pdf` service should contain Chromium. Exports then become River jobs; the API returns a job/export id and the PWA downloads the finished file from `/exports/*`.

## 6. Markdown ZIP reuse

All three families start from the same rendered SVG file:

- In family C the SVG is sent as a multipart asset (`diagram.svg`) and referenced by filename from `index.html` (gotenberg requires flat, filename-only references) or inlined; the identical bytes go into the ZIP next to `note.md`.
- In family B the SVG is the converter's input and the ZIP asset.
- In family A (canvas) there is no SVG on the PDF path at all unless canvas's SVG renderer is used to emit it — canvas can render to SVG as well as PDF, so one drawing routine could emit both.

To keep converters and browsers happy, the SVG renderer should stay in the "static SVG" subset: no `foreignObject`, no external `use` references, no scripting, no filters (resvg's list of unsupported features and Skia's rasterization rules both bite here: <https://raw.githubusercontent.com/linebender/resvg/main/docs/unsupported.md>, <https://skia.org/docs/user/sample/pdf/>). Fonts should be referenced by family name (`font-family="Noto Sans Devanagari, Noto Sans, sans-serif"`) so the same file renders in the PWA, in Chromium, and in any offline viewer.

## 8. Recommendation

**Use headless Chromium in the worker container, driven from Go over CDP, to print an HTML rendering of the Note to PDF. Start with gotenberg's `8-chromium` image as a separate Compose service; switch to chromedp + a `chromedp/headless-shell`-based image with `fonts-noto-core` added if the 478 MB image or the extra HTTP hop becomes a problem.**

Why:

1. It is the only option where *both* the Diagram and the note body get correct Devanagari shaping and stay selectable, with no custom typography code. Hindi in body text is the requirement that sinks families A and B in their cheap forms.
2. The PDF is produced from the same HTML/CSS and the same SVG the PWA already renders, so export fidelity tracks the UI for free, and tablet-oriented page sizing, page breaks and "Page n of m" footers are plain CSS (Chrome 131+ margin boxes) or `headerTemplate`/`footerTemplate`.
3. Vector output is guaranteed by Chromium's Skia PDF backend for paths and text; the diagram SVG just needs to avoid filters.
4. Everything involved is MIT/BSD; there is no runtime license key (unlike unipdf) and no AGPL component.
5. The API container stays Chromium-free: exports are River Jobs executed by the worker (or a `pdf` service the worker calls), matching spec 13's rule that heavy tooling lives only in the worker image.

Trade-offs accepted:

- Image size and memory: +143–478 MB and ≥512 MiB RAM for the PDF service. Affordable on a 24 GB single-owner host, but it must be capped (`mem_limit`, `--init`, restart policy) and treated as untrusted-input-adjacent: disable JavaScript for the export page if not needed (`--chromium-disable-javascript`), deny outbound URLs (gotenberg deny-list), and inline or ship all assets.
- Chromium upgrades become an operational item (gotenberg tracks Debian's Chromium; headless-shell publishes daily builds).
- Tagged/accessible PDF is available (`generateTaggedPDF`, gotenberg `pdfua`) but its quality depends on the HTML semantics we emit.

Fallback if Chromium is rejected on size grounds: **tdewolff/canvas** rendering both PDF and the SVG asset directly from Diagram JSON, with all text (body and diagram) drawn through canvas's HarfBuzz shaper and Noto Sans Devanagari embedded. Before committing to it, verify with a prototype that its PDF writer emits ToUnicode CMaps for shaped glyphs (unverified here) and accept hand-written page layout.

Not recommended: rsvg-convert + fpdf/gopdf composition (body-text Hindi unshaped), oksvg/rasterx and resvg (raster only), unipdf (commercial key), svg2pdf.js/jsPDF (needs a browser DOM anyway and no shaper), typst/svg2pdf crate (unmaintained per its README).
